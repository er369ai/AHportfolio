The problem

Recurring work is easy to script once and hard to run for a year

A script that automates a task is a weekend. A system that runs hundreds of those tasks unattended, survives a third party going down mid-run, and can be explained to an auditor eighteen months later is a different piece of engineering entirely.

The brief was a platform non-engineers could operate: schedule work, see what ran, understand what failed and why, and retry it without asking a developer. That requirement drove the data model before it drove a single screen.

What we built

Four decisions that shaped it

01

Schema before screens

Jobs, runs, attempts and results were modelled as first-class records. Every later feature — reporting, retries, permissions — was a query against that, not a new table.

02

Queue-backed execution

Work is dispatched to idempotent workers, so a retry cannot double-charge, double-send or double-write. Failures land in a dead-letter queue with their input intact.

03

Reporting that admits failure

The dashboard leads with what did not work. Silent success is the default state and needs no attention; the exceptions are what the interface is for.

04

An operator’s interface

Designed against real run volumes, not seed data: dense tables, keyboard-first filtering, and a retry that is one click from the row that failed.

Architecture

A model at the centre, everything else replaceable

DataRelational and normalised; migrations in version control, no schema drift between environments.
APIOne versioned contract used by the interface and by clients — no private back door for the UI.
Background workQueue with retry policy, backoff and dead-letter capture per job type.
IntegrationsEach third party behind its own adapter, so an upstream change is a one-file change.
InterfaceServer-driven, mobile-first, accessible; measured on a mid-range phone.
ObservabilityStructured logs and an audit trail per run, queryable by the operator, not just by us.
Outcomes

Operated by the client, not by us

Volume and uptime figures for this build are available on request.

Day-to-day scheduling and retries are handled by non-technical staff without developer involvement.
Third-party outages degrade a single integration instead of stopping the platform.
Every run is reconstructable after the fact, with its inputs, attempts and result.
New job types ship as configuration and one adapter, not as a new subsystem.
